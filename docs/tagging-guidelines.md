# Tagging Guidelines

This document defines how tags should be assigned across work themes and
projects.

## Core Rule

Use both theme tags and project tags, but give them different roles:

- Theme tags describe the broader area, question, or intellectual direction.
- Project tags describe concrete methods, signals, technologies, materials,
  interaction modalities, or application contexts.

Theme tags answer: "What larger area does this work belong to?"

Project tags answer: "What is specifically used, studied, or built here?"

## Theme Tags

Theme tags should be abstract and reusable across multiple projects.

Good theme tag examples:

- `Neuroadaptive Interaction`
- `Human-AI Interaction`
- `Subjective Experience`
- `Sports Performance`
- `Self-Regulation`

Guidelines:

- Prefer 3 to 5 tags per theme.
- Use research areas, high-level concepts, or application domains.
- Avoid highly specific implementation details unless they define the theme.
- Do not use project-specific system names as theme tags.

## Project Tags

Project tags should be concrete and specific to the project.

Good project tag examples:

- `EEG`
- `IMU`
- `EDA`
- `Playback Control`
- `Virtual Softness`
- `Kendo`
- `Remote Meetings`

Guidelines:

- Prefer 4 to 6 tags per project.
- Use concrete methods, signals, sensors, technologies, target tasks, or
  application contexts.
- Avoid broad area labels when the parent theme already communicates them.
- Repeating a theme tag is acceptable only when the term is central to the
  project itself, not merely inherited from the theme.

## Relationship To Outputs And Awards

Outputs and awards can keep their own tags for venue-facing classification,
such as `Poster`, `Demo`, `Domestic (Japan)`, or `Award`. These tags serve a
different purpose from work theme and project tags.
